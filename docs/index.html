Four languages, one laptop

The same 18 tests, written in C++, Python, R and JavaScript, run on one machine to see how each language uses its CPU, memory and GPU.

Code and raw data on GitHub All four languages computed identical answers on all 18 tests

Overall speed, relative to C++

Each test's best rate divided by C++'s rate on the same test, averaged geometrically within each hardware area, then across the four areas. 1× is as fast as C++.

Every test

Speed relative to C++ on a log scale, so 0.01× and 10× fit on one axis. Hover a row for the measured rates and the spread across three full runs. Plain loops are where Python and R fall furthest behind; library calls are where they catch up.

Using all cores

The same Mandelbrot work split across 1 to 12 workers. The CPU has 6 physical cores with two threads each; past 6 workers only C++ and JavaScript keep gaining. Python and R start separate processes, and their workers stop scaling earlier.

Memory

Bandwidth against the memory's theoretical peak of 51.2 GB/s (DDR4-3200, two channels). One core reaches about half of it; R copies arrays element by element and stays near 5 GB/s.

GPU (integrated Radeon, 7 compute units)

C++, Python and R run identical OpenCL kernels; JavaScript runs a line-by-line WebGPU translation. Once a kernel runs, the language barely matters. Moving data does: R has no 32-bit number type and converts every value, so its uploads and downloads are about 10× slower.

How much of the hardware each language reaches

Best measured rate as a share of the theoretical peak. The CPU peak assumes all six cores at full boost, which this 15 W chip cannot hold; matrix multiply goes through the same OpenBLAS library in every language.

Heat and clock speed during a run

One full run, sampled every second. The CPU reaches about 100 °C within seconds of heavy work, and the average clock falls well below its 4.4 GHz peak, so all-core results are partly limited by cooling.

What the numbers say

  • JavaScript is the surprise. Node's JIT compiler runs plain loops and Mandelbrot at C++ speed and scales to 8× on 12 workers, for 0.75× of C++ overall. Deep recursion (0.13×) and GPU uploads (0.16×) are its weak spots.
  • Python is two languages in one. Plain Python runs at 1–5% of C++ speed, but NumPy matches or beats C++: sorting is 7.4× faster thanks to SIMD instructions, and big allocations 4× faster thanks to huge pages. Parallel work stops at about 5×.
  • R is the slowest at plain code. Recursion is 573× slower than C++ and R's environments make a slow hash map. Where R hands work to BLAS it matches C++, and its sort is 1.3× faster.
  • C++ sets the pace for plain code, memory bandwidth and GPU transfers, and scales best across cores (9.3× on 12 workers).
  • The hardware, not the language, sets the ceiling for matrix math (about 225 GFLOP/s in every language through OpenBLAS) and for GPU compute (about 790 GFLOP/s, half the GPU's peak).

How it was measured

Each language implements the same specification: the same algorithms, the same inputs (generated from one formula, not each language's random generator) and the same output format. Loop-heavy tests use smaller sizes in Python and R, and every result is a rate (work per second), so sizes don't affect the comparison. Each test runs five times after a warm-up; the median counts. The figures above come from the newest of three full runs; the run-to-run spread is in the tooltips (typically about 1%).

Before each language, the runner waits for the CPU to cool below 60 °C. The laptop was on AC power with the balanced power profile. A verify mode runs tiny identical inputs and checks that all four languages produce the same answers; they do, to the last digit for integer results.

To add a machine, clone the repository and run:

./run_all.sh --check     # what is installed, per language
./run_all.sh             # about 7 minutes; results go to results/<machine>/

Full definitions are in common/SPEC.md, and the analysis notebook with more charts is analysis.ipynb.
