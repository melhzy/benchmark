Four languages, three laptops

The same 18 tests, written in C++, Python, R and JavaScript, run on three laptops — Dell Inspiron 14 7425 2-in-1 on Linux, Alienware m16 R1 on Windows and Apple MacBook Pro (14-inch, M5 Pro) on macOS — to see how each language uses a computer's CPU, memory and GPU.

Code and raw data on GitHub

Read the results by workload

Start with the operation your application spends time on. The same language can approach C++ on a library call and fall far behind on a plain loop. Matrix multiplication depends on the installed BLAS; GPU work depends on both kernel execution and data movement.

These are throughput ratios for the recorded implementations and machines. Overall weights CPU single-core, CPU multicore, RAM and GPU equally; it does not predict application runtime, energy use or value for money. Flagged GPU compute results remain visible, with their effect on the score quantified in the GPU section.

      Findings and their limits

        How it was measured

        Each implementation follows the same test definitions and deterministic input formulas. Some performance sizes differ by language. Reporting work per second makes the units comparable, but does not remove size-dependent cache, algorithm or startup effects. Built-in operations use language-specific implementations; matching outputs does not imply matching machine instructions.

        Most tests have five timed repetitions after a warm-up. Parallel Mandelbrot and allocation have one measurement per configuration. The charts use the newest full-mode run of each language, which can come from different batches. Each headline test rate is the maximum of the configuration medians; C++'s triad may use multiple threads while the others use one. Tooltips show earlier full-mode ranges (on the , ).

        The runs describe these machines under their recorded conditions. Hardware, operating system and software versions change together, and run order is not randomized. A temperature rise or a score gap alone does not identify a cause. To test a proposed explanation, repeat with matched sizes, worker counts and library settings while varying one factor at a time.

        Allocation measures first use as well as allocation itself. NumPy documents Linux huge-page advice, which is a plausible contributor to the Dell result; a controlled run with that advice disabled is needed to estimate its effect here.

        To add a machine, clone the repository and run, on Linux:

        ./run_all.sh --check     # what is installed, per language
./run_all.sh             # full run; results go to results/<machine>/

        on macOS (with Homebrew and R installed):

        ./setup_macos.sh         # OpenBLAS, Python packages in .venv, npm packages, R's OpenCL
./run_all.sh --check
./run_all.sh

        or on Windows (PowerShell or cmd):

        powershell -ExecutionPolicy Bypass -File setup_windows.ps1   # OpenBLAS, OpenCL SDK, packages
.\run_all.cmd --check
.\run_all.cmd

        Full definitions are in common/SPEC.md, and the analysis notebook with more charts is analysis.ipynb.
